### P1：Mermaid 按需加载

- 本地当前构建的 274 个 HTML 均带 Mermaid script，其中仅 13 页有 `.mermaid` 图定义。
- 按今日两份地图的 173 个正式规范地址再次核对本地构建：173 页全部加载，仅 13 页含图。首页、CentOS 文章、CS329 鲁棒验证三页的线上 HTML 也确认带同一脚本，属于线上配置问题，并非只有本地旧缓存。
- 当前 URL：`https://cdn.jsdelivr.net/npm/mermaid@v9/dist/mermaid.min.js`。一次 curl `--compressed` 请求返回 200，实际下载 831,989 字节，解压后 2,777,841 字节。该数字是本次 CDN 协商结果，不代表所有浏览器都采用同一编码，也不能逐 PV 外推流量或性能增幅。
- 原因：`_config.stellar.yml` 的 `plugins.mermaid.enable: true` 全局开启。建议先按实际图定义/页面开关加载，保留现有 Mermaid 版本及图表样式。少量 front-matter 漏标页需先核对，不能简单关全局后遗漏真实图表。
- 验收：无图页不请求 Mermaid；13 个图表页均能完整渲染；冷缓存网络对照，测量前不宣称 LCP/INP 改善。[Mermaid 官方使用说明](https://mermaid.js.org/config/usage.html)描述脚本与图定义的关系；本次不照搬其新版本 API 升级旧站。

### P1/P2：横幅来源与懒加载有两套控制逻辑

- `source/js/plugins/article-images.js` 从 20 张横幅中随机选一张，对 `.banner img.bg` 直接重写 src。
- 线上 CentOS 与 CS329 鲁棒验证 HTML 的横幅是 `src=data:` 占位图、`data-src=/assets/banner/banner_4.jpg`；随机脚本不更新 data-src，而 vanilla-lazyload 随后也会将 data-src 写入 src。
- 因此文档里声明的 banner 不是运行中唯一来源，不能把静态 data-src 引用数当作每张横幅的实际展示分布。两者存在竞争和重复下载风险；本轮没有取得 Network 时序，不能断言每次访问一定下载两张图。
- 建议统一横幅 URL 的最终来源和加载责任，再评估按需加载。是否保留随机横幅需尊重原展示偏好；当前未修改随机行为、构图或图像像素。
- 验收：明确最终 URL；Network 中首屏每个横幅只加载所需资源，没有因 src/data-src 相互覆盖产生额外请求；对照显示与原偏好一致。

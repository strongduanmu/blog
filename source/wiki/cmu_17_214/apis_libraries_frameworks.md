## API 的承诺跨出了仓库

第 11 讲从一个容易忽视的区别开始：仓库内改签名，可以更新全部已知调用；公开 API 的调用者可能从未见过，也无法同步修改。

API 的表面包括签名、行为、错误和数据格式。边界后面的存储和算法可以替换，边界上的承诺则需要谨慎演进。应明确公开范围，避免辅助接口意外成为长期承诺。

## 让正确调用成为自然选择

一致的命名、默认值和示例帮助人和 Agent 推断用法。重复概念采用不同动词、单位不明确的数值，以及能交换顺序的同类型参数，都可能诱发错误。

课件中的 `book(a, b, c, d, flag)` 改为接收 `BookingRequest`，包含用户标识、会议室标识和经过验证的时间区间。类型与构造入口可以排除一部分非法状态，网络输入仍需要在边界验证。

![将可混淆的参数改成表达领域约束的请求类型](/wiki/cmu_17_214/apis_libraries_frameworks/booking-request.webp)

补充说明：TypeScript 中两个普通 `string` 别名仍然可以互换，需要品牌类型或包装对象等方式建立区分；一个 `TimeRange` 也需要保护构造和可变状态，才能持续保持区间有效。课件表达的是约束方向，具体语言实现仍需核实。

错误同样属于契约。状态码、失败形式和检查顺序变化，都可能破坏调用者的分支。文档示例也会被直接复制，应像代码一样检查。让一个只有文档上下文的 Agent 编写客户端，可以帮助发现 API 的歧义。

## 小接口与行为替换

接口隔离原则（ISP）要求调用者不依赖自己不用的方法。只需要查询的候补模块，可以依赖 `BookingReader`，无需同时承担写入接口的变化。

里氏替换原则（LSP）则要求实现满足其声称的行为。一个实现了 `BookingStore`、但 `save()` 总抛出“不支持”的只读存储，虽然可以编译，仍违反写入承诺。契约测试应对每个实现执行相同检查。

## 演进需要考虑隐含依赖

Hyrum’s Law 提醒我们，用户可能依赖所有可观察行为，包括未明确承诺的顺序、错误文本和字段。使用者越多，接口越难修改。

新增周期预约时，把 `book()` 返回值从单个预约改成数组，会破坏原调用者。增加独立操作通常更容易保留原有语义。新增字段是否兼容，也取决于读取者能否容忍未知字段，不能只看“增加”两个字。

废弃接口需要替代方案、并行运行、迁移步骤和明确时间。迁移脚本、兼容说明及端到端验证，可以降低调用者成本。

契约测试只观察实现是否兑现承诺，因此可以跨越重构与重生成。真实数据库的约束、权限和供应商错误，不宜完全依靠自写替身模拟；外部邮件、付款等副作用则适合替换，并检查替身自身是否遵守契约。

## 库与框架改变控制权

![库由应用调用，框架在既定流程中调用应用](/wiki/cmu_17_214/apis_libraries_frameworks/library-framework.webp)

库是应用主动调用的工具，框架则安排结构和调用时机，让应用在扩展点提供代码。浏览器事件、Express 路由和测试生命周期都体现了这种控制反转。框架提供约定，也使代码更难迁移出去。

Template Method 用基类固定导入流程，由子类实现解析步骤；Strategy 用组合替换解析器。前者适合步骤由框架确定的情境，后者便于独立测试、运行时替换和组合。

Adapter 则包装无法修改的外部 SDK，把供应商调用转换为自己的端口。它隔离技术细节，但自己的接口没有表达的供应商能力，也不会自动暴露出来。

## 复用与生成都需要负责

成熟依赖能够复用标准与边界经验，也会带来权限、更新和传递依赖成本。自写一个简单每周预约规则可能很短，支持完整日历标准、时区和夏令时则是更大的问题。

因此要判断实际需要多少语义、谁维护、错误会影响什么。Agent 既可能重复实现项目已有能力，也可能为单一函数引入庞大依赖。依赖变更应回到这些具体问题上评审。

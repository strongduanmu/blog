## 预约服务为什么难以测试

上一讲我们把任务拆到可以验证的范围，本讲继续看这些验证怎样实现。课件先给出一个 Java 会议室预约服务：直接读取 `LocalTime.now()`，在类内部创建 `BookingRepository`，预约时间已过或存在冲突时就返回，方法的返回类型是 `void`。

假设要求是“拒绝过去的预约”，测试该怎样构造？系统时间无法随测试设置，仓库也不能替换；即使调用结束，返回值也无法说明预约被拒绝的原因。问题发生在设计上，继续堆叠测试代码很难解决。

课程把这两种困难分别称为可控性（Controllability）和可观察性（Observability）。前者回答如何构造所需状态，后者回答如何判断行为发生。

顺着原始实现看，`public book()` 是测试能够调用的入口，`private repo` 则只能在类内部访问。返回 `void` 本身并不意味着一定无法测试副作用，但这个实现同时隐藏了存储对象，也没有提供事件等其他观察出口。因此，测试既难设置条件，又难检查结果。**可测试性首先是设计属性**，不是多写几个测试就能补上的能力。

## 注入依赖，让业务规则独立

服务改为接收 `Clock`、仓库和通知接口，并返回 `BookingResult`。测试就可以固定当前时间，并检查 `IN_THE_PAST` 等结果。通知接口也允许替换成记录调用结果的实现。

下面保留课件中固定时间并检查预约结果的测试形状：

```java
@Test
void rejectsABookingThatStartsInThePast() {
    TestableBookingService service = new TestableBookingService(
        at(14, 0), new BookingRepository(), new RecordingNotifier());
    assertEquals(BookingResult.IN_THE_PAST,
        service.book("Gates 5117", new TimeInterval(600, 660)));
}
```

其中 `at(14, 0)` 是课件示例用于提供固定时钟的辅助方法，600 与 660 表示午夜后的分钟数，即 10:00—11:00。

纯业务规则不一定需要依赖一个时钟对象。如果规则只需要当前分钟数，直接传入数值即可；负责连接真实环境的服务，再使用 `Clock`。依赖注入的目的，是让需要变化的条件可替换，而不是给每个参数增加抽象。

![核心规则通过端口连接外部适配器](/wiki/cmu_17_214/testing_and_testability/ports-and-adapters.webp)

预约冲突判定可以进一步提取为接收营业时间、已有预约和请求区间的函数。这样测试规则时不需要数据库、网络或邮件服务器。端口由业务核心定义，适配器实现具体技术，内存替身也通过同一个端口接入。

课件还用购物车流程说明相同问题：查询数据库、调用配送 HTTP API、发邮件和通知 SAP 都写在一个循环中。此时想单独测试业务规则，也必须同时准备四种基础设施。将这些协作者接到端口上以后，我们才能在不启动外部系统的条件下检查核心规则，并另外验证适配器连接是否正确。

## 测试的层级与基本形状

单元测试检查最小的可测试部分，通常快速且便于定位；集成测试检查多个部分的连接；系统测试从用户入口驱动完整系统。三个层级逐步增加真实性，也逐步增加运行和定位成本。

测试通常遵循 Arrange、Act、Assert：构造状态，执行操作，检查结果。课件用已有预约之间的空档说明，输入和断言应对应明确的业务主张。一个测试可以有多个断言，只要它们共同描述同一行为。

测试名称也应说明条件与预期，例如“拒绝开始时间早于当前时间的预约”。当 CI 报告失败时，名称应帮助定位被破坏的约定。

下面按课件中的时间值展开一个 Arrange、Act、Assert 示例：

```java
@Test
void allowsABookingInAGapBetweenTwoOthers() {
    var existing = List.of(new TimeInterval(540, 600),
                           new TimeInterval(780, 840));
    boolean ok = canBook(existing, new TimeInterval(660, 720));
    assertTrue(ok);
}
```

已有预约是 9:00—10:00 和 13:00—14:00，请求是 11:00—12:00，因此预期允许预约。前两步分别准备状态和执行规则，最后的断言把“中间空档可用”变成机器可以检查的主张。TypeScript 的 `test` 与 `expect` 只是框架写法不同，表达的仍是同一个行为。

单元、集成和端到端测试常画成测试金字塔：底部有较多快速单元测试，上面保留适量集成测试与少量完整系统测试。下层便于定位，上层更接近真实连接；不能因为局部都通过，就省去数据库、通知器和入口真正装配后的检查。

## 测试替身要替代边界

测试替身实现与真实依赖相同的接口。记录型通知器把房间名写入列表，既可以检查预约结果，也可以检查是否发出通知；故意抛出异常的通知器，则能够稳定复现外部服务故障。

课件把能提供有效间接输入的替身称为 Responder，把故意注入错误的替身称为 Saboteur。例如让通知器抛出“服务不可用”异常，就可以稳定构造“预约已保存，但邮件失败”的情况。此时测试要检查什么，仍取决于业务契约：预约回滚、返回部分成功，还是记录可靠重试，必须先作出选择。

替身也不是越多越好。把核心规则也替换掉，测试就可能只检查“某方法被调用”。另一个问题是替身漂移：内存仓库总按某种顺序返回，而真实数据库未承诺这个顺序；通知替身永不失败，真实网络却会超时。替身验证局部逻辑之后，仍要用集成测试核对这些假设。

## 测试困难反映设计问题

课程结合 SOLID 讨论单一职责、依赖倒置和里氏替换：预约规则与基础设施分离，让一个变化有明确归属；服务依赖通知抽象；替换实现仍需要满足接口行为。

如果准备测试需要很多依赖、构造状态非常困难，或者每次重构都会让大量断言失效，就应回头检查职责和耦合。测试应观察调用者能依赖的契约，避免把私有字段、辅助方法名和不重要的调用顺序固定成要求。

同时要确认测试真正执行。课件展示 Maven 报告中的测试数量、失败、错误和跳过数。绿色的构建结果只能说明本次命令成功，不能证明预期测试都被发现。

具体检查设计时，可以沿实例化、调用、观察、替换和覆盖五个方面追踪困难：从全局环境读取配置会隐藏输入；内部 `new Database()` 让协作者难以替换；复杂规则只藏在私有方法中，可能意味着公共职责划分不合适；静态、`final` 与私有成员则限制部分替换方式。这里不是要求取消封装，而是先找出哪个业务行为缺少合适的测试边界。

测试代码本身也会给出信号。Arrange 需要大量依赖，可能是职责混杂；Act 很难满足前置条件，可能缺少可控入口；Assert 只能读取私有字段，可能缺少可观察结果。单一职责、开闭原则、里氏替换、接口隔离与依赖倒置，需要结合这些困难理解，后续设计课程会继续展开。

测试框架还有发现规则。Java 示例把测试放在 `src/test/java`，使用 `*Test.java` 名称和 `@Test` 注解，并通过 `@BeforeEach` 建立重复使用的准备状态。应阅读实际报告中的执行、失败、错误和跳过数量；文件存在或构建呈绿色，都不能证明新测试已被发现。

运行中的可观察性则需要进一步保留带时间的日志、可调日志级别与诊断状态。能够独立运行子系统、重放相关输入，才可能把线上故障转成可复现的测试；日志很多却无法还原条件，同样不利于排查。

## 如何审查生成的测试

生成测试常见的问题包括只覆盖正常路径、重复实现计算预期值、测试框架本身，以及执行代码却没有有效断言。预期结果需要来自需求，不能直接以当前实现的输出作为正确答案。

![测试需要独立于实现的预期依据](/wiki/cmu_17_214/testing_and_testability/test-oracle.webp)

阅读预约测试时，需要继续追问空列表、重复预约、包含关系，以及两个区间恰好相接时的行为。系统是否正确，取决于这些约定是否被检查，而不是测试文件有多长。

架构测试则补充检查另一类约定，例如领域模块不能导入基础设施、模块间不能成环。它们把已经决定的结构约束变成可执行检查，有助于发现 Agent 在持续修改中造成的结构漂移。

回到前面的预约测试，正常空档、部分重叠和完全相同只是三种情况。还应核对空列表、请求包含已有区间、已有区间包含请求、恰好相接，以及营业时间边界。读取 600、720 这样的数值时，先转成 10:00、12:00，才能判断这个测试究竟检查了哪一种关系。

测试也需要维护：重复准备可提取为 fixture，无依据的魔法值应说明含义，测试名称要与断言一致，复杂计算预期值的代码则可能再次需要验证。新增测试应带来新的行为主张。比如只检查第三方 CLI 框架接受 `--help`，通常不能说明自己的业务代码是否正确；但如果应用自行定义了帮助内容，那部分内容仍可成为应用契约。

最终，测试要回到每个委派任务的完成关卡中。包级快速测试适合在小步修改后运行，完整套件通过 CI 定期执行。我们在提交前需要确认相关行为经过了检查，并说明当前关卡尚未覆盖哪些系统连接。

## 架构是在子系统层面作设计

前面我们在类和模块之间分配数据、操作与职责。当系统扩展到预约、账户、计费等子系统，同样的问题还要再回答一次：谁拥有数据，通过什么操作协作，边界怎样安排？这些较难逆转的选择构成软件架构。

课件先介绍四种架构风格。它们可能提供相同功能，却在变化、验证与运行成本上有不同取舍：

| 风格 | 适合的问题 | 需要承担的成本 |
| --- | --- | --- |
| 管道与过滤器 | 构建、编译、数据处理等逐阶段变换 | 不适合频繁共享状态与来回交互 |
| 事件驱动 | 多个部分独立响应一次业务变化 | 行为分散，需要处理顺序与丢失 |
| 分层 | 表达、领域、存储等层次职责 | 一次纵向功能可能仍需修改多层 |
| 端口与适配器 | 核心稳定，外围技术可替换 | 每个边界都增加接口与装配成本 |

模式名称只提供结构词汇。我们仍要检查数据在哪里、一次操作跨过哪些边界、失败会停在哪里，而不是只在目录中建立同名文件夹。

## 运行调用与源码依赖可以不同

服务运行时需要调用存储，但源码可以依赖由领域定义的 `BookingStore` 接口，再让 Postgres 适配器实现它。这样替换数据库时，领域不用跟随变化。

![运行时调用存储，源码依赖则指向领域定义的接口](/wiki/cmu_17_214/software_architecture/dependency-rule.webp)

架构测试能够把领域不依赖存储、API 不绕过领域等规则变成构建检查。现有大项目引入规则时，也可以先记录已有违规，只阻止新增问题，再逐步清理。

图示需要与导入和实际数据访问核对。工具从代码生成依赖图，可以暴露草图没有画出的边；随后判断是实现有误，还是设计已经变化。

对于架构检查，课件给出三个判断问题：它检查哪一条具体主张，我们是否见过它失败，以及它的观察范围能否看见目标问题。单个类的行为测试无法发现其他领域类越过存储边界，导入规则可以；反过来，导入规则也看不见业务计数是否正确。

Java 可以用 ArchUnit 或 `jdeps` 查看依赖，TypeScript 与 Python 也有相应检查工具。课件引用 Flink 冻结历史违规的方式：先记录现有基线，仅阻止新增违规，再逐步偿还旧问题。工具生成的实际依赖图与设计图不一致时，应追查多出来的边，而不是直接让文档接受所有现状。

## 横切能力需要明确归属

HTTP 令牌解析属于入口适配器，领域接收识别后的用户；格式有效性在边界检查；无论请求从哪里进入都应成立的预约规则留在领域。请求日志与领域事件也可以分别处理。

这能避免领域函数接收会话字符串、HTTP 对象和第三方 SDK 类型。边界清楚以后，同一规则才能服务浏览器、CLI 和其他入口。

## 模块边界不必立即变成网络

子系统可以作为同一进程中的模块，也可以作为独立服务。独立部署带来 API、流水线、网络延迟和跨服务排障成本，应由独立变化、发布节奏、团队责任或审计要求支持。

一个预约动作原本直接调用账户模块，拆成服务后就要处理账户服务慢或不可用。两边单元测试都通过，仍不能证明连接处的行为正确。

每类数据还应有明确写入所有者。报表直接读取预约私有表，会把列名和存储结构变成跨团队契约；稳定 API、事件或明确导出格式能够提供更可控的边界。

服务边界还受组织沟通影响。课件借 Conway 定律提醒我们，使一个团队能够对某个边界完整负责，通常比按每个名词单独拆服务更容易维护。变化频率、发布节奏、扩容需求与审计要求不同，才更能支持独立部署。

同一团队的通知可以先作为订阅预约事件的模块，计费也可以保留清楚边界后再考虑抽离。跨子系统 API 仍需遵守前面讨论的命名、兼容与契约测试要求，网络不会减少调用者对行为的依赖。

数据所有权也不意味着其他部分不能持有副本。报表可以读取公开 API、订阅事件维护投影，或者消费由预约模块维护的稳定导出格式；直接读私有表，则让两边围绕列名与迁移重新耦合。

## 从计数规则判断所有权

学生等级由账户系统管理，但“当前有效预约不能超过上限”涉及预约与取消。若计数放在远端限制服务，只在预约时增加、取消时未减少，两个服务局部都正确，整体规则仍然错误。

课程据此审查一个六服务方案。小团队未必需要把计价、通知和分析都独立部署；首先需要跨预约与限制模块的失败检查，并明确谁更新计数。

## 模块化单体与统一入口

![同一部署中的模块仍可拥有明确的公开接口与私有实现](/wiki/cmu_17_214/software_architecture/modular-monolith.webp)

模块化单体保持一个部署单元，通过模块 API、私有实现和架构测试维持边界。其他模块经 API 或事件交互，不能随意读取内部数据。它降低分布式运行成本，但各部分仍一起发布和扩容。

Facade 为多个内部步骤提供简单入口，例如统一完成时段解析、计价和预约。它需要持续限制职责，否则也可能变成 God Class。

单体同样可以在代理后运行多个副本。复制进程以后，内存会话和计数不会自动共享，这正是下一讲的数据问题。

课件用 Segment 将一百多个小服务重新合并的经历，以及 Shopify 的模块化实践，说明服务数量不能直接代表架构质量。模块化单体也需要真实边界：每个模块公开 `api/`、隐藏 `internal/`，禁止其他模块绕过入口访问内部实现。

Facade 可以把查询时段、报价与创建预约编排成一个 `reservations.book()`。它降低普通调用者理解顺序的成本，但不能顺手接管所有规则；需要底层能力的合法调用者，也不一定必须绕过所有独立接口挤进同一个门面。

## 用架构约束 Agent 的修改

“实现 `BookingStore` 的 Redis 适配器”有端口和范围，“优化整个平台性能”则可能触及任何位置。任务最好沿着清楚边界展开。

大 diff 可以先检查新增的跨模块导入、领域对适配器的依赖，以及对其他子系统数据的写入。进一步要求每项检查说明检查的主张、是否能失败、是否真的能观察到目标问题。

课程还展示按目录加载的模块约定，让 Agent 修改领域代码时读到相应依赖规则。它仍属于上下文，需要与架构测试配合。评审大差异时，可以先列新增跨模块导入，再检查共享数据库写入，因为后者未必出现在导入图中。

回到六服务方案，最有价值的回应不是笼统要求“简化架构”，而是要求先演示取消后计数会失败的跨模块测试，再说明哪些数据由谁写入。只有这些检查能够覆盖连接处的问题，服务各自的绿色单元测试才有完整解释。

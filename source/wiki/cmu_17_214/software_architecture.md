## 架构是在子系统层面作设计

第 15 讲把数据、操作和结构放大到预约、账户、计费等子系统。架构选择通常难以逆转，主要差别体现在质量属性与维护成本，而不只是功能是否能实现。

管道与过滤器适合逐步转换数据；事件驱动适合多个部分对同一变化作出反应；分层让不同层承担不同职责；端口与适配器围绕领域核心连接技术边界。每种结构都要结合共享状态、交互方式和失败处理判断。

## 运行调用与源码依赖可以不同

服务运行时需要调用存储，但源码可以依赖由领域定义的 `BookingStore` 接口，再让 Postgres 适配器实现它。这样替换数据库时，领域不用跟随变化。

![运行时调用存储，源码依赖则指向领域定义的接口](/wiki/cmu_17_214/software_architecture/dependency-rule.webp)

架构测试能够把领域不依赖存储、API 不绕过领域等规则变成构建检查。现有大项目引入规则时，也可以先记录已有违规，只阻止新增问题，再逐步清理。

图示需要与导入和实际数据访问核对。工具从代码生成依赖图，可以暴露草图没有画出的边；随后判断是实现有误，还是设计已经变化。

## 横切能力需要明确归属

HTTP 令牌解析属于入口适配器，领域接收识别后的用户；格式有效性在边界检查；无论请求从哪里进入都应成立的预约规则留在领域。请求日志与领域事件也可以分别处理。

这能避免领域函数接收会话字符串、HTTP 对象和第三方 SDK 类型。边界清楚以后，同一规则才能服务浏览器、CLI 和其他入口。

## 模块边界不必立即变成网络

子系统可以作为同一进程中的模块，也可以作为独立服务。独立部署带来 API、流水线、网络延迟和跨服务排障成本，应由独立变化、发布节奏、团队责任或审计要求支持。

一个预约动作原本直接调用账户模块，拆成服务后就要处理账户服务慢或不可用。两边单元测试都通过，仍不能证明连接处的行为正确。

每类数据还应有明确写入所有者。报表直接读取预约私有表，会把列名和存储结构变成跨团队契约；稳定 API、事件或明确导出格式能够提供更可控的边界。

## 从计数规则判断所有权

学生等级由账户系统管理，但“当前有效预约不能超过上限”涉及预约与取消。若计数放在远端限制服务，只在预约时增加、取消时未减少，两个服务局部都正确，整体规则仍然错误。

课程据此审查一个六服务方案。小团队未必需要把计价、通知和分析都独立部署；首先需要跨预约与限制模块的失败检查，并明确谁更新计数。

## 模块化单体与统一入口

![同一部署中的模块仍可拥有明确的公开接口与私有实现](/wiki/cmu_17_214/software_architecture/modular-monolith.webp)

模块化单体保持一个部署单元，通过模块 API、私有实现和架构测试维持边界。其他模块经 API 或事件交互，不能随意读取内部数据。它降低分布式运行成本，但各部分仍一起发布和扩容。

Facade 为多个内部步骤提供简单入口，例如统一完成时段解析、计价和预约。它需要持续限制职责，否则也可能变成 God Class。

单体同样可以在代理后运行多个副本。复制进程以后，内存会话和计数不会自动共享，这正是下一讲的数据问题。

## 用架构约束 Agent 的修改

“实现 `BookingStore` 的 Redis 适配器”有端口和范围，“优化整个平台性能”则可能触及任何位置。任务最好沿着清楚边界展开。

大 diff 可以先检查新增的跨模块导入、领域对适配器的依赖，以及对其他子系统数据的写入。进一步要求每项检查说明检查的主张、是否能失败、是否真的能观察到目标问题。

## 设计漂移可以由合理修改累积而成

第 12 讲从持续演进的软件开始。用户需求变化，系统必须适应；每次增加特例和绕过边界，又会提高复杂度。课程借用 Lehman 定律解释这种张力，重构是主动控制复杂度的一种方式。

架构漂移（Architectural Drift）表示实现逐步偏离原设计。一次故障修复让 API 直接访问存储，随后新代码把这段例外当作先例，最终原有分层规则只留在文档里。

![一次未被管理的例外可能成为后续修改模仿的结构](/wiki/cmu_17_214/evolution_drift_memory/drift-autopsy.webp)

Agent 会复用眼前模式，也容易复制例外。更新文档去描述漂移后的实现，并不等于证明变化经过了设计决策。代码与测试帮助判断当前行为，契约和决策记录则帮助判断应该具备的行为。

## 对照决策检查漂移

把决策记录与导入、测试和请求路径对照，可以发现差异。若业务已批准改变候补优先级，应新增决策替代旧规则；若 API 无理由绕过服务，应修复实现；若存在真正必要的临时例外，则记录范围和重新检查条件。

课堂练习还包含误报：员工免除取消费本来就在记录中，不能只看到“免收费”就认定违规。Agent 报告需要逐条核对依据。

可以把结构约定转成架构测试，例如禁止 API 包直接依赖存储包，让偏离在修改时就被发现。指令文件也应随实现一起更新，否则 Agent 可能严格遵循已经失效的旧规则。

## 阅读陌生仓库先建立工作模型

课程建议先研究整体结构，再围绕准备修改的路径逐步缩小范围。目标是能够解释相关部分及连接关系，既不要求阅读全部源码，也不能只接受一段流畅总结。

阅读分成 Examine、Probe、Modify：先看构建、测试和历史，再运行观察，最后有目的地改变一个变量，比较预测与结果。预测错误时，应修正模型。

## 以 Jenkins 队列为例

构建文件先给出 Maven 模块边界。测试名称提示重启、崩溃和队列调度等行为；导入又揭示了持久化、安全和全局对象，这些未必全部出现在类注释中。

随后追踪任务从 `Queue.schedule2()` 到执行器的路径。Agent 需要给每一步提供当前快照中的文件与位置，评审者检查关键节点。课件使用断点确认入口，同时发现静态追踪遗漏了调用者和重载方法。

![请求追踪需要结合实际运行，核对入口和内部调用](/wiki/cmu_17_214/evolution_drift_memory/jenkins-request-trace.webp)

课件还改变默认静默等待时间并测量启动延迟，发现调度定时器是初始模型遗漏的因素。这些数值属于课程展示的实验，本站没有重新执行 Jenkins 实验，不把它们作为普遍性能结论。

探索记录应保存当前图示、请求路径、预测、观察和未解决的原因问题。这样后续重构能够使用已经核对的事实。

## 从证据恢复历史决策

决策考古（Decision Archaeology）追查的是为什么。证据包括项目文档、提交、issue、测试和配置，还需要使用被研究版本当时有效的记录。

Jenkins 队列通过快照供读取者访问，历史提交说明了减少 UI 线程锁依赖的动机；`Executor` 继承 `Thread` 的例子则主要找到后来的死锁代价，没有找到最初选择的理由。此时应把动机写成未知，不能从后果反推并虚构历史。

如果原作者可联系，直接询问可能比继续推断更有效。得到说明后保存来源和记录，让下一位维护者少做一次考古。

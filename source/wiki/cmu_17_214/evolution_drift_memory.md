## 设计漂移可以由合理修改累积而成

第 12 讲从持续演进的软件开始。用户需求变化，系统必须适应；每次增加特例和绕过边界，又会提高复杂度。课程借用 Lehman 定律解释这种张力，重构是主动控制复杂度的一种方式。

架构漂移（Architectural Drift）表示实现逐步偏离原设计。一次故障修复让 API 直接访问存储，随后新代码把这段例外当作先例，最终原有分层规则只留在文档里。

![一次未被管理的例外可能成为后续修改模仿的结构](/wiki/cmu_17_214/evolution_drift_memory/drift-autopsy.webp)

Agent 会复用眼前模式，也容易复制例外。更新文档去描述漂移后的实现，并不等于证明变化经过了设计决策。代码与测试帮助判断当前行为，契约和决策记录则帮助判断应该具备的行为。

这种偏离未必导致立即崩溃。假设存储一直依赖“预约按时间排序”，但假设既没有记录也没有测试；新导入入口写入无序数据后，查询可能静默返回错误。过期临时标记、未删除功能开关、不断增长的例外列表和人人绕行的模块，都是需要调查的信号。

临时例外可以保留，但要引用原规则、说明范围与重新检查条件。例如仅允许故障期间的报表入口直读存储，并要求在下一个同类入口出现前重新评审。这样后续维护者看到的是有边界的债务，不会把它当成新的默认结构。

## 对照决策检查漂移

把决策记录与导入、测试和请求路径对照，可以发现差异。若业务已批准改变候补优先级，应新增决策替代旧规则；若 API 无理由绕过服务，应修复实现；若存在真正必要的临时例外，则记录范围和重新检查条件。

课堂练习还包含误报：员工免除取消费本来就在记录中，不能只看到“免收费”就认定违规。Agent 报告需要逐条核对依据。

可以把结构约定转成架构测试，例如禁止 API 包直接依赖存储包，让偏离在修改时就被发现。指令文件也应随实现一起更新，否则 Agent 可能严格遵循已经失效的旧规则。

课堂的四项发现也要分别处理：报表直读存储可能需要修复或有依据的临时例外；已获批准的会员优先，需要替代原先先到先得的记录；员工免除取消费本就符合 ADR，属于误报；批量入口若仍以“服务暂不支持”为由绕过边界，而服务已经支持批量操作，这项理由就已经失效。

课件用 ArchUnit 表达“API 包不得依赖 storage 包”，也举了导入白名单的做法。规则能在本地或 Hook 中失败，Agent 才能在生成过程中看到约束；只把它放在很晚的 CI 环节，会延迟反馈。指令文件的库名与运行方法也要随迁移一起更新。

## 阅读陌生仓库先建立工作模型

课程建议先研究整体结构，再围绕准备修改的路径逐步缩小范围。目标是能够解释相关部分及连接关系，既不要求阅读全部源码，也不能只接受一段流畅总结。

阅读分成 Examine、Probe、Modify：先看构建、测试和历史，再运行观察，最后有目的地改变一个变量，比较预测与结果。预测错误时，应修正模型。

## 以 Jenkins 队列为例

构建文件先给出 Maven 模块边界。测试名称提示重启、崩溃和队列调度等行为；导入又揭示了持久化、安全和全局对象，这些未必全部出现在类注释中。

随后追踪任务从 `Queue.schedule2()` 到执行器的路径。Agent 需要给每一步提供当前快照中的文件与位置，评审者再检查后续修改依赖的关键节点。

![请求追踪需要结合实际运行，核对入口和内部调用](/wiki/cmu_17_214/evolution_drift_memory/jenkins-request-trace.webp)

沿课件的 Jenkins 快照，调度路径经过 `schedule2()`、等待队列、`maintain()`、可构建状态、负载映射与执行器。文件行号属于该快照；阅读自己的版本时，需要重新定位，不能把旧行号当成当前证据。

测试类名又提供了另一张目录：`QueueCrashTest`、`QueueRestartTest` 暗示持久化和重启承诺，被禁用的测试及其原因则提示尚未验证的角落。导入中的 `XmlFile`、`XStream2` 和全局 Jenkins 对象，又补出类注释没有说明的依赖。

实际运行进一步校正模型：断点确认 HTTP 请求最终到达 `schedule2()`，但调用栈还包含原追踪漏掉的重载和入口。课件将默认 quiet period 从 5 秒改为 0，原环境三次启动等待由约 7—9 秒降为毫秒级，并据此发现队列还有 5 秒推进定时器。这里保留的是课堂探索过程，不是本站的复测结果，也不是通用性能保证。

## 从证据恢复历史决策

决策考古（Decision Archaeology）追查的是为什么。证据包括项目文档、提交、issue、测试和配置，还需要使用被研究版本当时有效的记录。

Jenkins 队列通过快照供读取者访问，历史提交说明了减少 UI 线程锁依赖的动机；`Executor` 继承 `Thread` 的例子则主要找到后来的死锁代价，没有找到最初选择的理由。此时应把动机写成未知，不能从后果反推并虚构历史。

如果原作者可联系，直接询问可能比继续推断更有效。得到说明后保存来源和记录，让下一位维护者少做一次考古。

判断历史决策时，需要区分“当年为什么做”与“今天带来什么后果”。Jenkins 队列快照的提交记录能直接支持减少 UI 锁等待的动机；执行器继承线程的初始提交却只说明布局变化，后来的死锁修复只能证明后果。缺失的动机应该保留为未知。

这也是 Chesterton’s Fence 在代码阅读中的含义：先查清反直觉结构承担了什么，再决定是否移除。阅读记录应随手保留已确认事实、推测、运行结果与开放问题，作业四的 `ARCHAEOLOGY.md` 则要求为判断提供引用。工程记忆既包括找到的理由，也包括目前没有证据的部分。

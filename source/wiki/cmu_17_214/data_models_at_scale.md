## 把一个进程复制成两个以后

第 16 讲把预约服务放到代理后运行。每个副本在内存里保存令牌、有效预约计数和空闲缓存，同时从共享数据库读取预约。

一个副本签发的令牌可能在另一个副本失效；每个副本只数自己的预约，就可能共同超过上限；两个副本都先检查空闲再插入，还会发生重复预约。无状态服务意味着请求间状态有合适的外部归属，并不意味着整个系统没有状态。

## 检查必须运行在出错的拓扑中

![多副本计划中的进程内锁，不能约束其他副本](/wiki/cmu_17_214/data_models_at_scale/replica-plan.webp)

课件中的 Agent 计划使用粘性会话和进程内锁。粘性会话无法解决副本失效后的可替换性，进程锁也无法约束其他进程。单进程测试通过，不能证明多副本不变量成立。

Docker Compose 用服务名连接数据库、API 和代理，`--scale` 增加副本。验证应经过代理，并确认所有副本实际接收请求，例如检查 `X-Upstream` 标记。课件通过同一时段的并发预约检查，先展示失败，再检查修复。

示例中的 `UNIQUE(room, slot)` 适用于固定时段标识。补充说明：任意长度区间的不重叠，不能简单等同于起止值唯一，仍需要适合区间约束的数据库或事务方案。

## 把性能要求写成可失败的主张

“在每秒 200 次预约下，95% 请求少于 500 ms”同时规定负载与延迟分位数。平均值可能隐藏少量极慢请求，容量附近的排队也会抬高尾延迟。

流量模型需要包含查询与预约比例、热门房间竞争和突发行为。没有两个请求竞争同一时段的压测，就无法暴露重复预约。

![共享锁与数据库约束方案在课件实验中呈现不同扩展曲线](/wiki/cmu_17_214/data_models_at_scale/scaling-curves.webp)

课件实验用一、二、四副本比较共享大锁与数据库约束方案。图中数据是原课实验结果，说明瓶颈可能在共享资源；本站未复现实验，也不把倍率推广到其他环境。

信任测量前，还要检查 Docker CPU 配额、每轮初始数据、代理发现情况和真实错误率。副本数量改变，数据库查询与连接也会增长，瓶颈可能移向数据库。

## 持久化边界与数据寿命

领域对象到行、文档或事件的映射属于设计。循环读取会议室的预约，看起来像字段访问，却可能产生 N+1 次数据库往返，少量数据的功能测试很难发现。

选择存储应从操作出发。预约涉及跨用户与房间查询、事务和约束，关系存储有相应优势；令牌按键查询，可以考虑键值模型；事件保留历史，但需要计算当前状态并维护旧事件兼容性。

主键也会传播到其他系统。可变化的邮箱作为主键，会让邮箱更新影响全部引用；独立标识符能够减少这种传播，但仍需明确身份与生命周期。

## 每一份副本都需要一致性约定

缓存、读副本和读模型都可能滞后。空闲显示短暂过期，可以让最终预约操作明确拒绝；预约不变量则不能仅依靠旧缓存保证。

检查缓存一致性需要写入一个副本，再从每个副本读取。读模型应有数据来源、维护所有者和重建方式，不能让有意反规范化变成无人负责的重复数据。

事务边界还影响子系统划分。需要一起变化的数据尽量放在同一边界；按房间分片后，跨房间的用户上限就可能需要跨片协调。

## 数据结构逐步演进

![扩展、迁移、收缩分别部署，避免新旧代码同时运行时不兼容](/wiki/cmu_17_214/data_models_at_scale/schema-evolution.webp)

增加取消原因时，可以先加可空列，再由新代码写入并回填旧数据，最后收紧约束。每一步都要检查当时仍运行的版本，事件字段同样需要兼容旧读取者。

迁移文件应版本化并评审。备份还要实际恢复，明确可丢失的数据量和恢复时间。回退 Git 提交无法恢复已删除列中的数据，因此数据模型与迁移不能仅以代码可回滚来判断风险。

## 把环境与代码一起交付

第 19 讲从“本机正常”解释部署困难。运行时版本、系统库、路径、配置和权限都可能影响行为，生产环境未必恰好与开发机器一致。

镜像打包应用及其用户态运行依赖，容器是镜像的一次运行实例。容器共享宿主内核，虚拟机则拥有独立客体内核，因此启动成本与隔离边界不同。

![容器共享内核，虚拟机包含独立操作系统与内核](/wiki/cmu_17_214/containers_and_cloud/containers-vms.webp)

构建一次以后，应让测试和生产使用同一镜像，环境差异通过启动配置注入。标签可以移动，摘要则标识具体内容；需要可复现时，不能只依赖 `latest`。

课程先展示 Java 多阶段构建：构建阶段使用 Maven，运行阶段只保留 JRE、产物和启动文件，并使用非 root 用户。

## 云平台没有接管全部责任

虚拟机提供较多控制，也要求维护操作系统；托管容器减少放置与重启工作；函数平台进一步隐藏进程生命周期。不同抽象层仍保留应用、数据、配置、访问身份和依赖方面的责任。

按需、长期承诺与可被回收的闲置容量，适合不同负载。可中断批处理与持续预约服务不能直接采用同一恢复假设，闲置机器、磁盘和数据库也可能继续计费，因此实验结束要按部署清单回收资源。

区域和可用区影响距离、故障相关性与数据驻留要求。托管服务的共享责任边界也要明确。课件以 Snowflake 客户账户凭证泄露为例，说明托管平台不代替客户管理身份、认证与密钥轮换。

### 沿请求路径检查部署

排障可以沿 DNS、负载均衡、端口和容器逐跳检查。名称解析成功，只排除了这一跳的错误。Lab 4 中主机将 8080 映射到容器的 8080，应用却在 9090 监听，所以仍无法连接。

模板同时声明机器、安全组与启动脚本：`-p` 决定主机与容器端口映射，`-e PORT` 决定应用监听位置，安全组决定哪些来源能访问主机。三者需要一致。修复参数后重新创建栈，才能让声明与真实环境重新一致。

基础设施即代码把机器、网络和部署配置纳入版本控制，便于重复执行与评审。直接在运行机器上临时修改，却不更新模板，也会产生与代码、文档相似的漂移。

## 数据不能放在可替换实例里

容器删除后，其可写层通常不会随新实例恢复。数据库需要明确持久存储，上传图片需要共享存储或对象存储，会话也不能仅留在一个 API 进程里。

Volume 能让数据独立于容器生命周期，但仍需要备份与恢复方案。重新部署旧镜像也不会恢复已变化的数据结构，应继续使用兼容迁移。

自动扩容同样存在延迟：发现负载、创建副本和预热都需要时间。容量追上需求之前，需要决定排队、拒绝和重试策略，避免超时重试继续放大压力。

Compose 练习中的数据库没有 Volume、发布了 5432，也没有重启策略。这几项需要按环境评估：持久数据丢失与不必要的外部暴露通常优先；`${DB_PASSWORD}` 只说明文件没有直接写明密码，还要检查变量来源和使用方式。`depends_on: [db]` 也只表达启动关系，不能直接证明数据库已经可用。

编排器接收期望状态并持续调谐，例如保持六个指定镜像副本。Compose 启动栈与完整集群调谐不同，容器退出后是否恢复，还依赖重启策略。课件用区域故障说明：现有机器仍运行时，创建新实例的控制面也可能失效，所以只依赖出事后临时扩容并不充分。

## 设计容易启动和停止的服务

可运行性来自启动速度、健康状态、无状态处理和优雅退出。Liveness 判断进程是否需要重启，Readiness 判断是否应继续接收流量，两者不能混用。

收到 `SIGTERM` 后，可以先停止接收新请求，再处理在途工作，并在期限内退出。健康检查还应反映服务是否真正可用，而不只是进程还活着。

Twelve-Factor 的相关习惯把前面几项连接起来：配置从环境注入，日志输出到 stdout 交给平台收集，实例可以快速启动与退出。它们让同一镜像能够被替换，也让运行状态更容易观察。

健康检查的动作需要区分。课件中的普通 Compose 可以标记 unhealthy、让其他服务等待健康，却不会仅因 unhealthy 自动重启容器。数据库暂时不可用时，Readiness 可以停止接流量，Liveness 不宜简单跟着失败，否则可能让所有应用反复重启而不解决数据库故障。

密钥从受控配置注入，避免写进镜像与仓库。可以用 `docker history` 和 `docker image inspect` 检查层历史与环境；若旧层已经含有密钥，应重建无密钥镜像并轮换凭证。只在后续层删掉文件，不能移除已有副本中的密钥。

## 阅读 Dockerfile 的运行结果

回到部署文件，课件给出一个 Agent 生成的 Node Dockerfile。它直接复制整个目录后安装依赖，可能带入 `.env`、Git 历史和开发依赖，每次代码变化还会使依赖层失效。改进版先复制依赖清单并按锁文件安装，再复制应用，并配合 `.dockerignore`。

![依赖先于应用复制，运行镜像使用受限用户](/wiki/cmu_17_214/containers_and_cloud/reviewed-dockerfile.webp)

Node 镜像评审则比较了课件环境中的约 1.18 GB 与 251 MB，以及依赖安装重跑和缓存复用。数字来自该构建，通用方法是查看基础镜像、复制顺序、锁文件、开发依赖、忽略文件与运行用户，再实际测量。

## 给 Agent 一个可靠起点

固定的部署模板和约定，可以减少每次从零审查的范围。评审仍需要检查持久化、暴露端口、镜像版本、非 root 身份、健康检查、退出与凭证来源。

课程最后用内存会话、本地上传和恒定返回 200 的健康接口说明：一个服务能够启动，只证明部署流程的一部分，尚不能证明它可以安全替换副本。

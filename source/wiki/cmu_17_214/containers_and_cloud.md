## 把环境与代码一起交付

第 19 讲从“本机正常”解释部署困难。运行时版本、系统库、路径、配置和权限都可能影响行为，生产环境未必恰好与开发机器一致。

镜像打包应用及其用户态运行依赖，容器是镜像的一次运行实例。容器共享宿主内核，虚拟机则拥有独立客体内核，因此启动成本与隔离边界不同。

![容器共享内核，虚拟机包含独立操作系统与内核](/wiki/cmu_17_214/containers_and_cloud/containers-vms.webp)

构建一次以后，应让测试和生产使用同一镜像，环境差异通过启动配置注入。标签可以移动，摘要则标识具体内容；需要可复现时，不能只依赖 `latest`。

## 阅读 Dockerfile 的运行结果

课程先展示 Java 多阶段构建：构建阶段使用 Maven，运行阶段只保留 JRE、产物和启动文件，并使用非 root 用户。

生成的 Node Dockerfile 则直接复制整个目录后安装依赖，可能带入 `.env`、Git 历史和开发依赖，每次代码变化还会使依赖层失效。改进版先复制依赖清单并按锁文件安装，再复制应用，并配合 `.dockerignore`。

![依赖先于应用复制，运行镜像使用受限用户](/wiki/cmu_17_214/containers_and_cloud/reviewed-dockerfile.webp)

多阶段构建、基础镜像选择和安装范围应对应项目需要。课件的体积与缓存测量属于示例环境，不能仅凭基础标签推断所有项目的最终体积。

## 云平台没有接管全部责任

虚拟机提供较多控制，也要求维护操作系统；托管容器减少放置与重启工作；函数平台进一步隐藏进程生命周期。不同抽象层仍保留应用、数据、配置、访问身份和依赖方面的责任。

区域与可用区影响延迟及故障范围，云资源也可能在闲置时持续计费。实验结束需要按原始部署清单回收机器、磁盘和相关资源。

排障可以沿 DNS、负载均衡、端口和容器逐跳检查。Lab 4 的示例中，代理映射到 8080，应用却在 9090 监听。修复应回到基础设施配置，重新建立一致环境，而不是只在运行机器上临时修改。

基础设施即代码将机器、网络和部署声明纳入版本控制。真实环境的手动变化也会产生漂移，需要与声明核对。

## 数据不能放在可替换实例里

容器删除后，其可写层通常不会随新实例恢复。数据库需要明确持久存储，上传图片需要共享存储或对象存储，会话也不能仅留在一个 API 进程里。

Volume 能让数据独立于容器生命周期，但仍需要备份与恢复方案。重新部署旧镜像也不会恢复已变化的数据结构，应继续使用兼容迁移。

自动扩容同样存在延迟：发现负载、创建副本和预热都需要时间。容量追上需求之前，需要决定排队、拒绝和重试策略，避免超时重试继续放大压力。

## 设计容易启动和停止的服务

可运行性来自启动速度、健康状态、无状态处理和优雅退出。Liveness 判断进程是否需要重启，Readiness 判断是否应继续接收流量，两者不能混用。

收到 `SIGTERM` 后，可以先停止接收新请求，再处理在途工作，并在期限内退出。健康检查还应反映服务是否真正可用，而不只是进程还活着。

密钥应从受控配置注入，不能写入镜像层。后面删除一层中的文件，也不能保证旧层不再含有密钥；已经泄漏的密钥需要轮换。

## 给 Agent 一个可靠起点

固定的部署模板和约定，可以减少每次从零审查的范围。评审仍需要检查持久化、暴露端口、镜像版本、非 root 身份、健康检查、退出与凭证来源。

课程最后用内存会话、本地上传和恒定返回 200 的健康接口说明：一个服务能够启动，只证明部署流程的一部分，尚不能证明它可以安全替换副本。

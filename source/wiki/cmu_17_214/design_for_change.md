## 一个小需求为什么会修改十个文件

“取消预约后停止发送提醒”，看起来只是一个小需求。课件展示的真实修改却涉及十个文件：提醒逻辑散落在处理器、工作流和通知模块中，只改其中一处还不能完成修复。我们可以沿着这次变化，继续检查原来的模块边界。

面向变化的设计，需要让可能发生的变化保持局部。无法准确预测未来每项需求，但可以识别存储技术、通知渠道和业务策略等不同变化来源，避免它们互相牵连。

课件用一项覆盖 39 个生产代码库、约三万文件的研究说明变化成本：研究中的低质量代码缺陷更多，修复耗时也更长。它引用的 15 倍缺陷、平均多 124% 修复时间等数值，属于该研究样本，不能直接换算成任意项目的收益。我们在自己的系统中仍要追踪具体修改。

预约系统接下来会增加候补、周期预约、权限和分级计价。与其提前实现所有功能，不如分别询问：存储替换会影响哪里，新增通知渠道会影响哪里，修改预约规则又会影响哪里？这些问题把“容易变化”转成了可以检查的路径。

## 耦合不只出现在 import 中

耦合（Coupling）描述模块之间的依赖。直接访问 `Room` 的预约列表和存储内部结构，会让调用者同时依赖多项实现决定；通过 `isFree()` 和 `addBooking()` 等操作，只依赖对外承诺。

![不同模块连接方式形成不同的变化传播范围](/wiki/cmu_17_214/design_for_change/coupling-graphs.webp)

信息隐藏要回答“这个模块隐藏了什么可能变化的决定”。它可以隐藏存储格式、算法或第三方 SDK。依赖方向尽量朝向稳定的领域概念与接口，适配器再连接变化较快的技术。

依赖不只出现在直接调用中，课件进一步区分了几种形式：

| 类型 | 示例与影响 |
| --- | --- |
| 数据耦合 | `overlaps(slotA, slotB)` 只传入需要的数据，依赖体现在签名中 |
| 控制耦合 | `process(data, true, 2)` 让调用者了解内部模式，参数含义难辨 |
| 隐藏耦合 | 管理模块清空共享静态价格表，预约报价随之改变，即使双方没有互相导入 |
| 时间耦合 | 必须先调用 `loadRooms()` 再调用 `book()`，次序只存在调用者记忆中 |

因此导入图只能提供一部分证据。课件展示三种连线结构：一个中心连接六条边、两两互连十五条边、只连相邻模块六条边。边数相同也不代表风险相同，还要看中心是否承担过多职责、共享状态是否形成图外依赖。

Lab 4 则把边界落实到部署：应用只读取 `PORT`，模板接收镜像与端口，业务代码无需知道 EC2。环境接错时应修复配置；如果为更换机器而重写预约规则，就说明技术边界已经泄漏。

## 内聚让相关职责聚在一起

内聚（Cohesion）关注一个模块内部的内容是否服务同一目的。预约、计费、照片处理和导出报表都放进 `BookingManager`，会让一个类因多个无关原因变化。

高内聚并不意味着按代码行数拆得越细越好。相关操作与信息需要保持一致，每增加一个边界，也会增加调用、理解和维护成本。

内聚也有不同依据。功能内聚让全部内容服务同一个目标；顺序内聚把解析、校验、保存这样前后传递结果的步骤放在一起；偶然内聚则只是多个工具函数碰巧共用一个文件。类很短并不保证职责清楚，类很长也不能单凭行数定罪。

长 getter 链又会暴露多层内部结构。Law of Demeter 要求避免越过对象访问它的内部协作者，Tell, Don’t Ask 则建议把相应行为交回对象。课件的包裹练习可以帮助理解：`Shipment` 穿过 `Box.getItems()`，再逐个读取 `Item.weight`，于是知道了两层内部结构。若箱子自己回答重量，装运对象就只需要累加箱子的结果。这样箱子改变包装或重量计算时，调用者不必一起理解内部细节。

## 用责任分配解释候补晋升

课程使用 GRASP 的几个启发式原则来分配行为：

| 原则 | 在预约系统中的含义 |
| --- | --- |
| Information Expert | 拥有预约信息的对象负责判断空闲 |
| Creator | 拥有初始化信息或包含关系的对象创建预约 |
| Controller | 独立入口接收系统操作，避免规则藏在 UI 中 |

这些原则需要合作使用。候补晋升同时涉及队列、会议室和通知，把全部逻辑放进 `Room` 会让它承担过多变化原因。可以让 `WaitlistPolicy` 决定下一位，`Room` 管理占用，`Notifier` 负责通知，再由服务编排。

![候补策略、会议室和通知由服务协调](/wiki/cmu_17_214/design_for_change/waitlist-coordinator.webp)

沿着这张图比较新需求，就能判断哪种变化被隔离、哪些部分仍要一起修改。

Protected Variations 用稳定接口隔离变化；Pure Fabrication 允许创建领域中没有、但有助于职责分配的服务类；Indirection 则通过中间对象减少双方依赖。这些都是手段，不要求每个对象都对应现实事物。

Controller 还有两种常见粒度。操作较少时，一个 `ReservationSystem` 可以接收预约、取消与查询；操作逐渐增多时，可以按 `BookRoom`、`CancelBooking` 等用例拆分。前者入口少，却容易膨胀；后者职责集中，却增加了导航成本。GRASP 给出的是判断线索，不能替我们选择粒度。

回到候补例子，我们也能具体比较变化：新增短信主要改 `Notifier`，增加计价主要接入新的策略；周期预约仍可能修改服务与会议室中的预约数据，不能声称协调器让所有变化都只改一个文件。Lab 3 中已经存在却从未被调用的 `BookingPolicy`，则说明有时需要先接通现有边界，而不是继续创建新的抽象。

## 模块边界也是委派边界

低耦合限制 Agent 修改的影响范围，高内聚让相关内容能够进入一个聚焦的上下文。任务计划可以明确模块、允许触及的接口与检查方法。

是否增加抽象，要看变化概率、调用者是否由自己控制，以及能否说出第二个真实实现。为永远不会发生的变化预先解耦，也会成为今天的复杂度。

最后可以按课件练习追踪四项修改：内存存储换成 Postgres，首先检查端口和适配器；按小时计价，需要找出费用计算与返回契约；增加房主审批，会影响状态模型、操作和权限规则；新增日历视图，则尽量通过已有查询接口读取。具体影响以实现为准，这些是分析方向。

候补计划也可以分成三条明确关卡：先独立测试队列顺序和删除，再在取消流程中检查空队列与单个候补的晋升，最后只在 API 增加只读展示。按功能、验收检查或分层切任务都可以，前提是每一步的边界和验证能说清楚。

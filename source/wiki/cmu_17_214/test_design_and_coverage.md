## 测试通过以后，还需要问什么

第 4 讲从“312 个测试全部通过”开始。测试数量并不能说明选择了正确的行为，也不能证明错误实现会被发现。课程沿着规格、输入选择、覆盖率和变异测试，逐步讨论怎样提高验证的有效性。

## 把正确性写成契约

一个操作的前置条件约束调用之前的状态，后置条件描述执行后的承诺，不变量则需要在相关操作前后持续成立。

例如，账户取款要求 `amount > 0` 且余额足够；成功后的余额减少相应金额；账户余额始终非负。前置条件被违反时，责任首先属于调用者，而公开 API 仍应在信任边界验证输入并清楚失败。

规格需要足够精确。“排序列表”没有说明是否升序、是否稳定、是否修改输入，以及空值如何处理。只有补充这些条件以后，才能把它们逐条转成测试。规格同时为代码生成提供输入，也为测试预期提供依据。

## 等价类与边界值

测试无法穷举全部输入，需要先把输入划分为行为相似的等价类。课件中的运费函数有四个区间：

| 重量 `w`（kg） | 结果 |
| --- | --- |
| `w <= 0` | 拒绝无效重量 |
| `0 < w <= 5` | 收费 5 |
| `5 < w <= 20` | 收费 `5 + (w - 5)` |
| `w > 20` | 拒绝超重 |

每个区间选择代表值，再检查 0、5、20 及附近输入。若重量允许小数，“附近”应依据精度选择，不能把所有边界都默认按整数加减 1。

![运费等价类与边界探测](/wiki/cmu_17_214/test_design_and_coverage/shipping-boundaries.webp)

预约区间采用 `[start, end)` 时，9:00—10:00 与 10:00—11:00 不重叠。只测试明显分离和明显重叠，会漏掉 `<` 与 `<=` 的差别。因此还需要相接、进入一分钟和相隔一分钟的测试。

多个条件组合时，可以用决策表合并无关情况。课件的支付例子按是否使用额度、额度是否足够、现金是否足够，决定使用哪种余额或失败；已经由前一个分支决定的变量，可以在表中标成无关。

## 用性质覆盖更多输入

基于性质的测试（Property-based Testing）先声明对一类输入都应成立的关系，再由框架生成输入。例如编码与解码往返后应恢复原值，账户经过一系列合法操作后余额不应为负。

失败后，框架会缩减输入（Shrinking），把很长的操作序列压缩为仍能触发问题的反例。这让生成测试既能探索，也能留下可以理解的失败依据。

性质本身仍需要审查。`reverse(reverse(xs)) == xs` 是一个有用关系，却不能独自证明 `reverse` 的全部要求；恒等函数也能满足它。这里补充的例子说明，性质与具体示例应结合使用。

测试驱动开发则按失败测试、最小实现、重构循环推进。Agent 可以提出测试草稿，但哪些断言构成契约，仍需要人在实现之前决定。

## 覆盖率检查运行过什么

语句覆盖率统计执行过的语句，分支覆盖率统计条件各个方向，路径覆盖率统计完整执行路线。有循环时，可行路径可能非常多，甚至没有有限上界。

覆盖率没有检查断言的质量。即使所有语句和分支都执行过，也可能没有触及危险数值。课件的 `scale(a, z)` 在 `a <= 1` 时令除数为 `a - 1`；已有测试分别走两个分支，仍会漏掉 `a = 1` 的除零问题。

因此，红色区域帮助发现未执行代码，绿色区域只表明运行经过。把 100% 当成目标，还可能促使生成大量弱断言测试。更合理的做法，是优先补足关键行为和风险路径，并解释有意留下的缺口。

## 用变异检查断言是否有效

![注入小错误后重新运行测试，观察变异是否被发现](/wiki/cmu_17_214/test_design_and_coverage/mutation-testing.webp)

变异测试会把 `+` 改成 `-`、`<` 改成 `<=` 等，再运行测试。如果测试失败，称为杀死变异；若仍通过，就需要调查测试是否遗漏了相关行为。补充说明：有些变异与原程序在可观察行为上等价，不能把所有存活变异都直接判定为真实缺陷。例如图中 `a > b ? a : b` 改为 `a >= b ? a : b`，在普通整数数值比较中结果相同，不能按图示直接期待测试杀死这一变异。

变异分数比执行覆盖率更接近“测试能否发现错误”，但每个变异都需要运行测试，成本较高。课程建议把这种方法用于正确性要求较高的部分。

完成测试设计后，应逐条对照规格，记录覆盖了什么、未覆盖什么，以及理由。规格测试与结构测试互相补充，集成测试还要检查模块连接处的假设。

## 一个副本也可能处理多个请求

第 17 讲先回到预约竞争。多副本放大了问题，但一个进程中的请求线程、后台任务和异步操作，也会交错访问共享状态。没有主动创建线程，并不代表业务逻辑按请求串行执行。

线程共享内存，进程通常通过外部系统交换数据，异步任务则在等待时让出执行机会。需要分析的是实际执行步骤如何交错，以及哪些状态同时共享、同时可变。

## 检查与执行之间存在空隙

预约先检查无重叠，再插入记录。两个请求可以都检查通过，然后分别插入。有效预约计数也可能发生读、加一、写回的丢失更新。

![两个请求都在另一个请求写入之前检查成功](/wiki/cmu_17_214/concurrency/double-booking-race.webp)

线程安全集合只保证相应单次操作，不自动保证多次调用的组合。`ConcurrentHashMap` 上先 `get()` 再 `put()` 仍可能丢失更新；`merge()` 等原子操作可以保护单键更新，但不自动把数据库插入和其他规则一起纳入原子边界。

可以先手动写出交错：A 检查空闲，B 也检查空闲，A 插入，B 再插入。每个线程内部都按正确顺序执行，组合后却违反约束。计数同理，A 与 B 都读到 2，各自写回 3，实际新增两次却只增加一次。

因此线程调度本身也是测试输入。单核也可以在线程之间切换，不需要多个 CPU 才产生竞争；网络消息、后台取消与请求处理都可能引入相同问题。安全审查应先找共享且可变的数据，再决定同步、消除变化或消除共享。

## 同步、不可变与独占所有权

锁让同一临界区中的操作按顺序执行，也提供相应内存可见性。关键是所有相关访问使用同一把锁。每个请求新建一个服务对象时，实例上的 `synchronized` 保护的是不同对象，不能形成共同约束。

大锁可能限制吞吐；按会议室加锁能减少无关等待，却不一定保护跨房间的用户上限。两项操作反向获取多把锁，还可能死锁。固定获取顺序可以打破循环等待，超时则需要配合释放已持有资源与恢复逻辑。

不变数据减少同步需求，但不可变对象引用的内容也必须受到保护。Java `record` 中的可变列表不会自动变成不可变列表。另一种办法是线程封闭，让一个所有者修改状态，其他线程通过请求与它交互。

安全性要求坏事不发生，活性要求工作能够继续，性能要求工作及时完成。修复一个维度时，需要检查是否损害其他维度。

死锁的四个条件是互斥、持有并等待、不可抢占与循环等待，破坏其中一个就能阻止相应死锁。两个请求交换房间时若分别先锁 A、先锁 B，就可能互等；统一按房间 ID 从小到大加锁，可以打破循环。超时还必须释放已持有资源，否则只是把等待换成另一个未完成状态。

可见性是另一个维度。没有正确同步时，一个线程未必及时看到另一个线程的写入；锁与原子变量提供语言内存模型规定的保证，不能把“测试中总能看到”当成保证。

不可变性则需要贯穿对象内容。`TimeRange(Instant start, Instant end)` 的成员也不可变；包含 `List` 的 record 需要复制并保护列表。线程封闭让唯一所有者处理可变状态，其他线程通过消息请求，重新获得局部顺序推理的条件。

## 将跨进程不变量交给共享存储

数据库唯一约束能拒绝相同时段标识，任意区间重叠则需要更合适的约束，例如 PostgreSQL 排斥约束。它们能覆盖访问同一受约束数据库的多个写入路径。

课件还给出带条件的计数更新：

```sql
UPDATE students
SET active = active + 1
WHERE id = $1 AND active < 3;
```

受影响行数为零，表示没有取得名额。补充说明：若预约还需要另一条插入语句，两者应在合适事务中一致提交，并处理失败回退；单条计数更新不能独自证明完整预约流程原子。

## await 仍然允许交错

先 `await isFree()`，再 `await insert()`，两个任务同样可能都读到空闲。单线程事件循环没有消除等待点之间的竞争。

未等待的 Promise 还可能丢失错误，后台通知完成顺序也可能不同于请求顺序。线程池和工作队列限制执行数量，但仍需定义容量、失败和共享数据规则。事件订阅者也可能与新的预约竞争同一时段。

课件还用 Jenkins `XmlFile` 比较两种状态：`writing` 是 `ThreadLocal<File>`，记录当前线程写哪个文件；`beingWritten` 是同步 Map，记录所有线程正在保存的对象。前者通过不共享避免冲突，后者共享所以需要同步。若把它们都简化成普通静态字段，单次保存测试仍可能通过。

接口和类注释应说明并发约定，例如只读可共享、写入需要某把锁。`@GuardedBy` 等声明还可交给分析器检查。异步订阅者同样需要遵守约定：取消后候补晋升与新请求可能争抢刚释放的时段，Observer 的低耦合并不会自动序列化它们。

## 主动控制交错来测试

普通并发测试只观察少数调度顺序，重复通过不能证明不存在竞争。压力测试提高出现问题的机会；强制交错测试则在选定位置暂停一个请求，让另一个完成，再恢复第一个。

![暂停第一个计数读取，再让第二个请求填满队列](/wiki/cmu_17_214/concurrency/forced-interleaving.webp)

候补队列例子先填到上限减一，让请求 A 读取后暂停，再让 B 插入，最后恢复 A，从而稳定触发越界。测试必须与实际实例生命周期一致，不能用“多个线程共享一个服务”的测试替代“每请求一个服务”的部署。

审查生成并发代码时，可以先列出共享可变状态、所有读写位置与保护机制，再核对测试究竟控制了什么顺序。线程安全承诺也应写入接口与类说明。

强制交错测试的关键，是让 A 在读取计数后暂停，B 填满剩余名额，再恢复 A，最后检查总数没有越界。课件提供 `PausingStore` 控制这个位置；测试还按真实控制器为每个请求创建服务实例，才不会误用同一对象锁。

这个测试稳定覆盖了选定顺序，不能证明所有交错都安全。压力测试补充探索其他时序，数据库约束则在其覆盖范围内直接拒绝非法写入。判断一个修复时，应分别说明它保护的是单进程缓存、多个线程，还是访问同一数据库的多个副本，避免把一种范围的保证推广到另一种范围。
